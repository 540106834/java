# 🎯 场景：逻辑删除学生

目标：

```
PUT /api/students/{id}/disable
```

把：

```
status = 1 → 0
```

---

# 🧱 第一步：Repository

```java
public int disableById(Long id) {

    String sql = """
        UPDATE student
        SET status = 0
        WHERE id = ? AND status = 1
    """;

    return jdbcTemplate.update(sql, id);
}
```

重点在这里：

```
WHERE id = ? AND status = 1
```

它同时完成了：

* 是否存在
* 是否已删除
* 幂等控制

如果已经是 0，就不会更新。

数据库帮你做完判断。

---

# 🧱 第二步：Service

```java
public void disableStudent(Long id) {

    int rows = studentRepository.disableById(id);

    if (rows == 0) {
        throw new RuntimeException("学生不存在或已停用");
    }
}
```

一句话解释：

> 影响 0 行 = 没命中

没有任何模糊空间。

---

# 🧱 第三步：Controller

```java
@PutMapping("/students/{id}/disable")
public String disable(@PathVariable Long id) {
    studentService.disableStudent(id);
    return "ok";
}
```

---

# 🧪 测试

```
curl -X PUT http://localhost:8080/api/students/1/disable
```

成功：

```
ok
```

如果再执行一次：

```
学生不存在或已停用
```

你会发现一件事：

我们没有写：

* findById
* exists
* null 判断

数据库已经帮我们做完所有验证。

---

# 🧠 这叫“原子校验”

一条 SQL 同时完成：

* 查
* 校验
* 修改

没有竞争问题。
没有并发窗口。
没有重复查询。

这就是工程里常见的写法。

---

# ⚙️ 为什么它优雅？

想象两种写法：

### 方式 A

1. 先查
2. 判断
3. 再更新

中间如果被别人改了呢？

你会遇到“幻觉数据”。

---

### 方式 B（我们现在用的）

数据库一次性处理。

要么成功。
要么 0 行。

没有中间状态。

这像一扇只能单向通过的闸门。🚪

---

# 🎯 总结口诀

> 不需要旧数据 → 直接 update
> 需要旧数据 → 先查
> 高并发 → 优先合并进 SQL
