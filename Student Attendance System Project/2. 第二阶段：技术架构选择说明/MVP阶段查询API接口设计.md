# 🎯 一句话核心原则

API 的数量 = 前端页面真正需要的数据种类

你现在的查询页面只需要两类数据：

1. 班级列表
2. 某个班级某天的考勤数据

所以设计了两个接口。

不是随便两个，是刚刚好两个。

---

# 🧠 从页面倒推接口

想象一下你的查询页面：

```
[ 班级下拉框 ]   [ 日期选择器 ]   [ 查询按钮 ]
--------------------------------------------
           表格区域
```

页面运行时会发生什么？

### 第一步：页面加载时

它必须知道有哪些班级可以选。

否则下拉框是空的。

所以需要：

```
GET /api/classes
```

✔ 这是一个独立数据源
✔ 和考勤数据无关
✔ 可以被多个页面复用

---

### 第二步：用户点击查询

页面要告诉后端：

* 我要查哪个班级
* 我要查哪一天

于是自然变成：

```
GET /api/attendance?class_id=1&date=2026-02-25
```

✔ 查询是带条件的
✔ 是聚合统计
✔ 是只读操作

这就是第二个接口。

---

# 🏗 为什么不合并成一个接口？

比如有人会问：

> 能不能一个接口把班级列表和考勤一起返回？

技术上可以，但设计上不好。

原因：

1. 页面加载时不一定马上查询考勤
2. 班级列表属于基础数据
3. 考勤查询属于业务数据
4. 分开更清晰，职责单一

这叫：

> 单一职责原则

---

# 🧩 这两个接口分别属于什么类型？

| 接口                | 类型     | 角色     |
| ----------------- | ------ | ------ |
| `/api/classes`    | 基础数据接口 | 字典类接口  |
| `/api/attendance` | 业务查询接口 | 聚合统计接口 |

---

# 📐 如果系统变大，会怎样？

以后可能会增加：

* `/api/student/{id}` 查看学生详情
* `/api/attendance/month` 月报
* `/api/attendance/export` 导出Excel
* `/api/classes/{id}/students` 查班级学生列表

接口数量会随着“业务功能”增长。

但你现在的 MVP 页面只需要两个。

---

# 🌱 一个重要思维方式

接口不是为了“做系统”而设计。

接口是为了“支持一个具体页面”而设计。

页面有什么数据需求，接口就提供什么数据结构。

不是多，不是少。

刚刚好。
