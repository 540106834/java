数据血缘绑定，这四个字听起来像是数据库界的“家谱登记处”。
每一条数据，都不是凭空出现的，它有“父母”、有“加工厂”、有“搬家记录”，甚至还有“谁动过它”的指纹。

我们拆开讲。

---

## 一、什么是数据血缘（Data Lineage）

数据血缘，本质是：

> **一条数据从哪里来 → 经过哪些处理 → 变成什么 → 被谁使用**

像这样一条链路：

```
考勤机 → HTTP接口 → attendance_raw → 解析服务 → attendance_record → 统计报表
```

如果某天报表错了，你可以倒着查：

报表 → 统计SQL → attendance_record → 解析逻辑 → 原始报文

这条可追溯链路，就是血缘。

---

## 二、什么是“血缘绑定”

血缘绑定 = 把上下游关系**明确地关联起来**，让系统知道：

* 这条数据来源于哪个源数据
* 解析记录对应哪条 raw 数据
* 统计结果依赖哪批记录

换句话说：

> 不只是“知道流程”，而是数据库层面能追溯。

---

## 三、结合你现在的考勤系统举例

你现在有：

```sql
attendance_raw
attendance_record
```

如果你在 attendance_record 里加：

```sql
raw_id BIGINT
```

并且存的是：

```
attendance_raw.id
```

那就完成了一次“血缘绑定”。

关系变成：

```
attendance_raw.id
        ↓
attendance_record.raw_id
```

这样你可以：

```sql
SELECT *
FROM attendance_record r
JOIN attendance_raw raw
ON r.raw_id = raw.id;
```

这就是结构化血缘绑定。

## 四、血缘绑定的三种常见方式

### 1️ 外键式绑定（最简单）

表中加 source_id

优点：

* 简单
* 可靠
* 易查询

适合你当前 MVP 阶段。

---

### 2️ 业务字段绑定

例如：

```
device_sn + sn
```

作为逻辑血缘。

这种叫：

> 软血缘（逻辑血缘）

缺点是：

* 如果字段被改动
* 或出现重复

血缘就断了。

---

### 3️ 元数据血缘（企业级玩法）

例如：

* 通过调度系统（Airflow）
* 或数据平台记录 SQL 依赖
* 自动解析 SQL AST
* 构建字段级血缘图

这属于数据中台、数据治理领域。

阿里 DataWorks、字节 DataLeap 都在做这个。

---

## 五、字段级血缘 vs 表级血缘

### 表级血缘

```
A表 → B表 → C表
```

### 字段级血缘

```
A.device_sn → B.device_sn → 报表.设备号
```

字段级血缘更高级，也更难做。

## 六、为什么数据血缘这么重要

在你未来走向：

* Kafka
* 分布式
* 数据仓库
* BI系统
* 审计合规

血缘就是：

🧭 排错指南
🕵 审计工具
🧨 事故回溯地图
🧠 数据治理核心

没有血缘的系统，就像没有行车记录仪的高速公路。

## 八、进阶一点：血缘+幂等

如果你未来上 Kafka：

```
device → kafka → consumer → raw → record
```

你要保证：

* raw 唯一
* record 唯一
* 消费可重放
* 血缘不断裂

这时候血缘绑定就变成“系统韧性”的骨架。
